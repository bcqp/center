Replication materials

Data files, specifications and settings that let a reader repeat a brief’s results.

Purpose of replication materials

Replication materials allow readers to inspect how a reported result was produced and, where data access permits, rerun the analysis. A replication package should connect each published table, figure or estimate to the relevant source data, transformation steps, model specification and computational environment. The objective is computational transparency, not a guarantee that every result can be reproduced without access to restricted source data.

Recommended package structure

  • README: publication title, authors, version, package date and a concise run guide.
  • Data inventory: source institution, dataset/table, direct URL, retrieval date, licence and access conditions.
  • Data preparation: scripts for cleaning, merging, transformations, deflation, seasonal adjustment and sample construction.
  • Analysis code: complete scripts for estimation, diagnostics, tables and figures.
  • Model specification: equations, variable definitions, lag structure, priors or identifying restrictions where relevant.
  • Environment: software, package and engine versions, random seeds and computational settings.
  • Outputs: machine-readable tables and figures matching the published report.

Data provenance and access

Where data are publicly downloadable, the package should provide the source URL and retrieval date rather than silently redistributing files with unclear rights. For restricted or confidential data, provide code and instructions that can operate on an authorised local copy, without including protected observations. Source licences and terms remain applicable. The FAIR principles provide a useful framework for making research data findable, accessible under clear conditions, interoperable and reusable.

Computational reproducibility

Packages should record software and dependency versions, operating environment, random-number seeds, estimation settings, convergence criteria and any stochastic simulation settings. For Bayesian estimation, document priors, chains, warm-up, draws, convergence diagnostics and posterior summaries. For optimisation-based estimation, record starting values, tolerances, objective function and convergence status. If an online engine is used, record its version and model implementation.

Reporting and publication standards

Replication files should map directly to claims in the publication: identify which script generates each table or figure and state any output that cannot be regenerated. The American Economic Association data and code policy is a useful reference for documentation and verification expectations in empirical economics. It is cited as an external standard for reference; it does not imply AEA review or endorsement of BIQEP materials.

Versioning, archiving and citation

Each package should have a stable version identifier and a changelog describing corrections or changes. Where appropriate, archive a release with a persistent identifier through a repository such as Zenodo. Cite the exact package version used for a published result, not only a moving repository branch. Never overwrite a previously cited package without preserving the earlier version.

Limits and exceptions

Full replication may be constrained by licensing, confidentiality, third-party access conditions, discontinued source series or software dependencies. Such constraints should be stated clearly, with the maximum reproducible workflow supplied. A package is not described as fully reproducible if essential inputs or code are unavailable.
