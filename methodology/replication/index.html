Methodology

Replication

What is published with a brief so that a reader can repeat it.

Purpose of replication

Replication materials allow readers to inspect how a reported result was produced and, where data access permits, rerun the analysis. A package should connect each published table, figure or estimate to its source data, transformation steps, model specification and computational environment. Computational reproducibility does not guarantee that every result can be recreated without access to restricted source data or the original environment.

Minimum contents of a replication package

  • README: publication title, authors, version, package date, requirements and run instructions.
  • Data inventory: source institution, dataset or table, direct URL, retrieval date, licence and access conditions.
  • Data preparation: scripts for cleaning, merging, transformations, deflation, seasonal adjustment and sample construction.
  • Analysis code: complete scripts for estimation, diagnostics, tables and figures.
  • Model specification: equations, variable definitions, lag structure, priors or identifying restrictions where relevant.
  • Environment: software and package versions, random seeds and computational settings.
  • Outputs: machine-readable tables and figures corresponding to the publication.

Data provenance, access and licensing

When data are publicly downloadable, provide the source URL and retrieval date rather than redistributing files with unclear rights. For restricted or confidential data, provide code and instructions that operate on an authorised local copy without including protected observations. Licensing and access conditions remain applicable. The FAIR principles provide a useful framework for making research data findable, accessible under clear conditions, interoperable and reusable.

Computational reproducibility

Record software and dependency versions, operating environment, random-number seeds, estimation settings, convergence criteria and stochastic simulation settings. For Bayesian estimation, document priors, chains, warm-up, draws, convergence diagnostics and posterior summaries. For optimisation-based estimation, record starting values, tolerances, objective function and convergence status. For an online engine, record the engine version and model implementation used.

Reproducing OES-based analysis

  1. Open the OES browser workspace or obtain the source from the OES GitHub repository.
  2. Use the same dataset vintage and apply the documented cleaning and transformations.
  3. Select the estimator and enter the exact model specification, options and settings reported in the brief.
  4. Run diagnostics and compare the resulting estimates, tables and figures with the published outputs.
  5. Record any differences caused by software updates, numerical tolerances, random seeds or revised source data.

External documentation standards

The American Economic Association data and code policy is a useful reference for empirical documentation and verification expectations in economics. Zenodo can be used to archive versioned research outputs with persistent identifiers. These references do not imply AEA review, Zenodo endorsement or independent certification of BIQEP materials.

Versioning, corrections and limitations

Each package should have a stable version identifier and changelog. Where possible, archive a release with a persistent identifier and cite the exact version used for the published result. Never overwrite a previously cited package without preserving the earlier version. If full replication is constrained by licensing, confidentiality, discontinued source series or software dependencies, state the limitation and provide the maximum reproducible workflow available.
